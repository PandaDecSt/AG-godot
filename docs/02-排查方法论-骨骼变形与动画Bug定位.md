# 排查方法论：骨骼变形 / 动画 Bug 怎么定位

> 这篇有两个用途：
> 1. **复盘**："四肢变面条"这个 bug 到底错在哪，为什么之前十几轮都没找到。
> 2. **方法论**：一套能照抄的排查流程，换个项目、换个图形 bug 也管用。
>
> 前置知识见 `docs/01-入门-MMD模型是怎么被搬进Godot的.md`。

---

# 第一部分：这个 bug 到底是什么

## 1.1 现象

- 人物四肢、脖子被"拉成面条"，看不出人形
- 日志里 IK 求解器一直不收敛：`右足ＩＫ 距离 82.3286 → 64.0782`
- 改 IK 迭代次数、改角度限制、改插值……全都没用

## 1.2 根因（一行代码）

`mmd_builder.gd` 的 `_build_skeleton()` 里：

```gdscript
# ❌ 错误写法（面条根因）
global_rest[i] = global_rest[parent] * Transform3D(Basis.IDENTITY, pos)

# ✅ 正确写法
global_rest[i] = Transform3D(Basis.IDENTITY, pos)
```

PMX 的 `bone.position` 是**模型空间绝对坐标**。错误写法把它当成"相对父骨的偏移"，于是沿骨链**层层双重累加**。

**比喻**：A 说"我站在第 5 排"（绝对位置），代码理解成"我在爸爸的基础上再往后 5 排"。爸爸也这么算，爷爷也这么算……越往末端的骨头飞得越远，整排人被拉成一条长面条。

## 1.3 数字有多离谱

| 项目 | 正确值 | 错误写法算出来的 |
|---|---|---|
| 模型网格高度 | y ∈ [0, **22.1**] | —— |
| 骨架高度 | y ∈ [0, **21.4**] | 手指骨飞到 y ≈ **252**，头 y ≈ **102** |
| `右足ＩＫ` ↔ `右足首`（它要拽的脚踝）静止距离 | **0.0000** | **82.59** |
| 动画中该 IK 距离 | 0.01 ~ 0.08（求解容差） | 82.33 → 64.08（永不收敛） |

网格只有 22 单位高，骨架却被拉到 250 单位 —— 皮肤被这些飞出去的骨头拽着，自然成了面条。

**IK 为什么"永不收敛"也一起解释了**：IK 的任务是让脚踝去追控制骨。但控制骨被错误几何放在了 82 单位之外，人的腿总长才 13 单位左右 —— **它够不着**。所以求解器每帧都在拼命拉腿，把腿拉直、拉长、反折，这就是"某关节反折拉长"的来源。

## 1.4 修复后的验证数据（真实运行，非推测）

```
自检A 全局rest == flip(pos_raw)          最大偏差 = 0.000000
自检B 静止时 IK 骨 ↔ effector 距离
   右足ＩＫ    -> 右足首    0.0000
   右つま先ＩＫ -> 右つま先  0.0000
   左足ＩＫ    -> 左足首    0.0000
   左つま先ＩＫ -> 左つま先  0.0000
自检C 骨架高度范围 y = [0.000, 21.444]
```

帧 0 右腿链世界坐标（修复后）：踝 y≈**1.34** → 膝 y≈**7.49** → 胯 y≈**13.04** → 中心 y≈**9.76**。
正常人形比例，且 IK 骨与脚踝重合在 `(0.26, 1.35, −1.21)`。

# 第二部分：为什么之前十几轮都没找到

这部分比修复本身更值钱。**六个反面教训**：

### ① 只看现象猜原因，没先量数据

看到"面条"就猜 IK 有问题，于是去调 IK 参数；猜插值有问题，去改插值。
**"面条"只是最终画面**，而画面错误的可能来源有十几处（解析 / rest / pose 语义 / 蒙皮 / IK / 付与親 / 坐标系 / 材质）。在这种局面下猜，等于抽奖。

### ② 被注释和自己的假设骗了

代码注释明明写着 `bone.position 为模型空间绝对坐标`，**下一行却把它当父相对偏移用了**。
注释和代码互相矛盾，但因为"注释写得很自信"，反而没人去核对。

> 教训：**注释是别人的记忆，不是证据。** 只有跑出来的数字才是证据。

### ③ 没有"静止自检"这条基准线

一直在调**动画**，却从没验证过**静止时人形对不对**。
静止是最简单的状态（没有插值、没有时间、没有 IK 迭代）。**如果连静止都是错的，调动画一定是白费力气。**

### ④ 验证链条太长，无法二分

只靠"F5 看画面"来判断对错。从文件到像素中间有 8 个环节，画面只给出一个"对/错"的布尔值，**没法定位是哪一环**。

### ⑤ 用错了输入数据

早期一直用 `models/motion.vmd` 调试，它是给**另一个模型**的纯表情文件，骨骼轨道数 = 0，人根本不会动。
**这类错误会把所有后续结论污染掉**，因为你在测一个空输入。

### ⑥ "本机没显卡"被当成了"无法验证"

于是只能改代码 → 让用户 F5 → 用户描述现象 → 再猜。反馈一轮要几分钟，且信息量只有一句"还是变形"。
实际上 **Godot console 版 `--headless --script` 纯 CPU 就能跑完整逻辑并 dump 数字**，一轮只要几秒。

# 第三部分：这次做对了什么（五个关键动作）

### 动作 1：把"看画面"换成"看数字" —— 先定义可量化的不变量

在动手改任何代码之前，先写下**静止时必须成立的等式**：

- `全局 rest.origin == flip(pos_raw)` （骨架几何 = 文件里写的）
- `IK 控制骨的位置 == 它 effector 的位置`（MMD 骨架天生如此，距离必须是 0）
- `骨架 AABB ≈ 网格 AABB`（骨头不能跑到皮肤外面）
- `Python 独立复算的世界矩阵 == player._world`（代码自洽性）

这些等式把一个模糊的"变形"变成了**四个能打印成数字的布尔判断**。

### 动作 2：按数据流分层，从最静态的一层往上查

```
解析(pmx/vmd) → rest 几何 → pose 语义 → 世界变换累乘 → 付与親 → IK → 蒙皮
   ↑ 最静态，先查                                              最动态，最后查 ↑
```

查到 **rest 几何**这一层就发现 IK 骨和脚踝差 82 单位 —— **后面几层根本不用查了**。
（这也解释了为什么之前调 IK 全无效：错误在 IK 的**上游**。）

### 动作 3：双实现互证，确定 bug 不在"计算"而在"输入"

把 `dump.json` 里的 `_eff_pos / _eff_rot` 拿到 **Python 里用另一套代码重算一遍**世界矩阵，和 Godot 跑出来的 `player._world` 逐骨比对 —— **偏差 0**。

这一步的价值：证明 `vmd_player` 的矩阵累乘**数学上是对的**。
于是搜索范围一下砍掉一半：**问题不在计算过程，在喂给它的几何数据**。

### 动作 4：A/B 对照实验 —— 让两种解释各算一遍，看谁让不变量成立

这是决定性一击。对同一份 `pos_raw` 做两种假设：

| 假设 | 公式 | 4 条腿 IK 链的静止距离 |
|---|---|---|
| A：相对偏移（当前代码） | `global[i] = global[parent] + pos[i]` | **82.588** ❌ |
| B：绝对坐标（MMD 约定） | `global[i] = pos[i]` | **0.000** ✅ |

同时验证：假设 A 复算出的结果，和 `dump.json` 里的 `global_rest_origin` **偏差 0.0000** —— 反向证明**现有代码确实在用假设 A**。

**至此结论不是"我觉得"，而是"数据只允许这一种解释"。**

### 动作 5：排除干扰项，别修错东西

修之前先确认：网格和骨架**是不是同一尺度**？
实测网格 y ∈ [0, 22.1]、骨骼 `pos_raw` y ∈ [0, 21.4] —— 同尺度，**排除"缩放错配"**。

如果不做这步，很可能误判成"要给骨架乘个缩放系数"，加一个魔法数字盖住真 bug。

# 第四部分：可照抄的通用排查流程

任何"图形/动画看起来不对"的 bug 都能套这七步。

### 第 0 步：确认输入文件是对的
打印文件名、大小、解析出的条目数。**轨道数 = 0、顶点数 = 0 这类空输入会污染一切后续结论。**

### 第 1 步：写下不变量（断言）
不要写"看起来对不对"，要写**能算成数字的等式**，尤其是**静止/初始状态下必须成立**的那些。
> 这一步是整套方法的地基。没有不变量，后面全是猜。

### 第 2 步：按数据流分层，从最静态一层开始
先让"什么都不动"的状态正确，再谈"动起来"。静止错 → 动画必错，且现象会被放大得面目全非。

### 第 3 步：把中间结果 dump 成 JSON
不要在渲染管线里靠肉眼判断。把每一层的中间数据落盘成 JSON。
**没有 GPU 也能做**：headless / CPU-only 跑同一份逻辑。

### 第 4 步：用第二种语言独立复算
Godot 里 dump，Python 里重算。
- 两边一致 → 计算逻辑正确，去查**输入数据/语义**。
- 两边不一致 → 计算逻辑有 bug，往里挖。

这一步每次都能把搜索空间砍一半。

### 第 5 步：对可疑语义做 A/B 对照
凡是"这个字段到底是绝对还是相对 / 行主序还是列主序 / 左乘还是右乘 / 度还是弧度"这种二选一的语义歧义 ——
**别读文档猜，两种都算一遍**，看哪种让第 1 步的不变量成立。数据会自己选边。

### 第 6 步：改一处 → 重跑同一套断言
只改一个地方，然后**跑一模一样的那套断言**。
数字从 82.6 变成 0.08 才叫修好；"看起来好像好点了"不算。

### 第 7 步：把结论写回代码注释 + 日志
在踩坑那一行写 `★ 致命坑：...`，说明**为什么不能那样写**，并附上数字。
> 本次已写入 `mmd_builder.gd:101-108`，同步修正了 `dump.gd` 里同款公式（否则以后 dump 出的数据会和运行时矛盾，又是一个陷阱）。

# 第五部分：本项目专用速查

## 5.1 不变量清单（可直接抄进新的 verify 脚本）

| # | 断言 | 现值 |
|---|---|---|
| 1 | `global_rest[i].origin == flip(pos_raw[i])` | 偏差 0.000000 |
| 2 | 静止时 IK 控制骨与 effector 重合 | 4 条链全 0.0000 |
| 3 | 骨架 AABB ≈ 网格 AABB | 21.4 vs 22.1 |
| 4 | Python 复算 world == `player._world` | 偏差 0 |
| 5 | `player._eff_pos[i] == local_rest[i]`（无 VMD 平移的骨） | 偏差 0.000 |
| 6 | `pose = rest` 时蒙皮矩阵 = 单位阵 | `pose_test.gd` 已验证 |
| 7 | 帧 0 骨长 vs rest 骨长偏差 | ≤ 0.88（健康） |

## 5.2 症状 → 先查哪里

| 症状 | 最可能的位置 | 先跑什么 |
|---|---|---|
| **静止就变形** | rest 几何、pose 语义 | `dump.gd` → 查断言 1/2/3 |
| **四肢/脖子变面条** | rest 双重累加（本次根因） | 断言 1、2 |
| **静止正常、一动就镜像 / 往反方向弯** | `FLIP_Z` 只翻了一半 | 检查顶点 / 骨骼 / VMD 三处是否都翻了 |
| **关节反折、越拉越长** | IK 目标不可达（通常是上游几何错） | 断言 2；不要先动 IK 参数 |
| **完全不动** | VMD 文件错 / 骨名对不上 | 打印 `tracks` 数量、骨名匹配率 |
| **抖动、脚打滑** | IK 迭代、付与親顺序 | `verify.gd` 连续多帧看 IK 距离曲线 |
| **颜色/描边不对** | 材质与 shader，**跟骨骼无关** | 别去动骨骼代码 |

## 一句话总结

> **之前失败**：靠现象猜原因、只用画面当唯一反馈、跳过静止自检、信了注释。
> **这次成功**：先写死不变量 → 分层从最静态查起 → 换语言独立复算 → 对语义歧义做 A/B 对照 → 让数据自己选边。
>
> **面条的根因是一行 rest 计算把绝对坐标当成了相对偏移**；能找出来，靠的不是更聪明的猜测，而是**把"看起来不对"翻译成了"这个数应该是 0，实际是 82.59"**。
